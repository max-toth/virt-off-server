# Rules for virt-off-server C++ Development

## Interface-First Design

1. **Сначала интерфейсы, потом реализации.** Каждый этап кодогенерации начинается с создания чисто виртуальных классов (интерфейсов) и сборки каркаса — композиции из интерфейсов. Никакой реализации на этом этапе.

2. **Классы — только композиция вызовов интерфейсов.** Класс не содержит внутренней логики, а только делегирует работу интерфейсам, полученным через конструктор. Запрещено создавать классы, которые одновременно реализуют логику и вызывают другие интерфейсы — вызывать могут только композиты.

3. **Единая ответственность (SRP).** Каждый интерфейс описывает ровно одну сквозную функциональность. Интерфейс с несколькими разнородными методами — нарушение. Если в интерфейсе появляется группа методов, которые можно разделить — их нужно разделить.

4. **Никаких приватных методов, делающих разное.** Если в классе есть несколько приватных методов с разной семантикой — значит, это разные ответственности, и их нужно вынести в отдельные интерфейсы/классы.

5. **Интерфейсы документируются.** Каждый метод интерфейса снабжается комментарием: что делает, какие параметры ожидает, что возвращает, в каком состоянии может быть поток (thread-safe? reentrant?).

6. **Реализации следуют тем же правилам.** Класс-реализация интерфейса не может содержать логику, не относящуюся к контракту этого интерфейса. Если реализация становится сложной — её нужно разбить на под-интерфейсы.

## Workflow

1. Разработка начинается с проектирования интерфейсов и каркаса (файлы `.hpp`).
2. Результат отдаётся на ревью без какого-либо кода реализаций.
3. После утверждения интерфейсов пишутся реализации.
4. Изменение интерфейса после утверждения — через новый раунд ревью.

## Зависимости

- Включения только через интерфейсы: `#include "core/ILogger.hpp"`, не `#include "LoggerImpl.hpp"`.
- Класс, использующий интерфейс, ничего не знает о его реализации.
