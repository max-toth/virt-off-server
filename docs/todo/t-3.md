# Task: Серверное взаимодействие с предметами и ударами (Variant B)

Научить сервер арбитражу взаимодействий (взятие/бросок предметов, удары), чтобы
все клиенты видели одинаковую картину. Сервер — источник истины по владению
предметом и валидации удара; физику считает клиент-владелец.

API: v2. Манифест предметов при входе. Рассылка событий — всем, включая автора.

## Модель

Логически на сервере одна запись на предмет: PropRecord{id, key, owner_id, held}.
Сервер выдаёт канонические propId по манифесту сцены, выдаёт/отбирает владение и
рассылает события. Физику полёта/удержания считает owner_id и шлёт PROP_STATE.

## Протокол (заморозить в docs/ до реализации)

id = [len:1][utf8]; propId = uint32 LE.
Существующие: 0xFF CONNECT, 0xFE ASSIGN_ID, 0x01 VOICE, 0x02 POSITION.

| type | name          | напр.  | payload |
|------|---------------|--------|---------|
| 0x03 | ATTACK        | C→S    | [id][kind1][targetId][point12][impulse12][hitObject1] → validate+relay |
| 0x04 | PROP_STATE    | C→S    | [id][propId4][pos12][rot16][vel12][flags1] → owner-only + relay |
| 0x05 | SOUND         | C→S    | [id][sfx1][pos12][vol4] → relay |
| 0x06 | MANIFEST      | C→S    | [id][count2][{keyLen1|key|halfExtents12|mass4}*] |
| 0x07 | PICKUP_REQ    | C→S    | [id][propId4] |
| 0x08 | PROP_RELEASE  | C→S    | [id][propId4][vel12][angVel12][flags1] |
| 0x09 | MANIFEST_ACK  | S→C    | [count2][propId4 * count] |
| 0x0A | PROP_GRANT    | S→all  | [propId4][holderId][flags1] |
| 0x0B | PROP_RELEASE  | S→all  | [propId4][ownerId][vel12][angVel12][flags1] (owner пуст → FREE) |
| 0x0C | PROP_SNAPSHOT | S→C    | [count2][{propId4, ownerId, held1}*] |
| 0x0D | DISCONNECT    | C→S    | [id] |

flags в 0x0B: бит0 = успокоилось (owner пуст, FREE).

## Disconnect

drop(id) (graceful 0x0D) и sweep(now) (timeout) → общий код:
users.remove → props.release_all_of(id) → broadcast(PROP_RELEASE, owner="", FREE).

## Масштабирование (не сейчас, зафиксировать)

- Один сокет читается последовательно; несколько strand'ов распараллелят только
  обработку, но общее кресло и валидация «два клиента» не режутся по клиенту →
  вернутся локи и недетерминизм. Выгоды при текущем workload нет.
- При росте: тяжёлое (props/мир) — на один game strand, лёгкое — по клиентским;
  в пределе — процессы-«комнаты» (отдельный сокет/io_context на офис).
